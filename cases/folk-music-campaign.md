# 原来，有首民谣唱过我｜民谣营销活动策划与交互设计

**从一次情感共鸣，到愿意继续听一首民谣。**

[返回作品集](https://github.com/JingchunWang0109) · [体验交互 Demo](https://0d496e044b0944e69cc756bc75a80934.app.workbuddy.host/)

在网易云音乐民谣营销活动运营实训中，我围绕“如何让喜欢民谣的人更愿意持续收听”，完成产品分析、营销策略分析与活动策划，并将方案整理为 XMind 交互模型和可体验的网页 Demo。

**项目时间：** 2026.09–2026.10  
**我的角色：** 运营实训学员。用户调研由十人小组协作完成，我回收其中 201 份有效问卷并参与分析；其余报告与活动方案为个人完成。

> **作品说明：** 本作品为个人实训方案与交互展示，非网易云音乐官方活动，不代表平台上线计划。Demo 中歌曲、音乐人、歌词、参与人数和奖励均为演示内容；未接入网易云账号、真实曲库、模型或奖品系统。

## 一、先确定活动要改变什么

如果用户完成测试、分享一张结果图之后就离开，活动获得了传播，却未必增加了后续收听。

我希望回答的是：**如何让用户在参与和分享之后，还愿意回来听民谣？**

为此，我按照产品分析、用户调研、营销策略分析、活动策划四个阶段推进。前面的分析持续为最终玩法提供依据。

| 阶段 | 关注的问题 | 对活动设计的影响 |
|---|---|---|
| 产品分析 | 平台有什么可以利用的产品特点？ | 从评论、歌单与分享所承载的情感表达切入，借助免费试听降低体验门槛 |
| 用户调研 | 用户为什么参加，又为什么放弃？ | 缩短流程、故事选填、分享自愿，让奖励与兴趣相关 |
| 营销策略分析 | 如何让传播接到站内行为？ | 结果直接连接歌曲与收听，而不止是一张可分享的海报 |
| 活动策划 | 怎样将这些判断变成可执行规则？ | 用场景答题领歌，以收听进度获得抽奖机会，并设计回访与验证指标 |

策略分析覆盖网易云音乐、QQ 音乐、酷狗音乐三家官方微博的 64 个活动案例。我据此形成的设计判断是：延续情感表达的优势，同时补上从表达、分享回到收听的路径。这里是本次案例分析的判断，不代表对平台整体经营转化的定量结论。

## 二、调研如何影响玩法

十人小组共回收 **2,105 份有效问卷，其中我回收 201 份**。在本次样本中，55.4% 表示喜欢民谣，每周听民谣三次以上的占 36.7%；这提示我，活动可以关注从兴趣到收听习惯的距离。

这两个比例是样本整体的描述，不能据此直接计算“喜欢民谣用户”的收听转化率，也不代表平台全部用户。

| 样本中的发现 | 对应的设计选择 |
|---|---|
| 34.7% 将耗时长视为参与阻力 | 五道场景单选题，选择后自动进入下一题；以约一分钟为设计目标，实际用时通过测试验证 |
| 34.2% 反感拉好友要求 | 分享自愿，不以邀请好友作为领歌或抽奖条件 |
| 33.2% 认为规则复杂会影响参与 | 主规则简化为“答题领歌，听歌抽奖” |
| 43.0% 对人格测试感兴趣，37.6% 对故事与民谣结合感兴趣 | 用轻量场景题开始，再为愿意表达的人提供选填故事 |
| 想讲故事的人群中，40.3% 担心耗时，15.3% 有隐私顾虑 | 故事可跳过、提供句式提示，默认不公开原文，评选单独授权 |

上述比例来自实训问卷汇总，是本次方案的设计输入；不作为代表全部用户的市场估计。

## 三、三个关键设计选择

### 1. 先让人愿意参加，再给表达留空间

答题不考音乐知识，而是询问“此刻在哪”“想起谁”“希望歌曲陪你做什么”等生活场景。即使不熟悉民谣，也能进入活动。

完成五题后，用户可以写一段不超过 100 字的故事，也可以直接领歌。句式提示帮助用户开始表达，跳过入口则避免将写作变成负担。

![故事选填与隐私说明](https://github.com/user-attachments/assets/504059f8-800b-4e3f-8046-47f6da6d2e4b)

*图 2：截图中使用我为演示填写的示例故事。故事选填、原文不出现在分享卡中，参与评选需要另行勾选授权。*

### 2. 结果是一首可以听的歌，并解释匹配原因

结果页给出歌曲、歌词和“为什么是这首”，将用户选择的生活场景与歌曲联系起来，再提供试听入口。

我希望用户感受到自己的经历被回应，而不只是得到一个抽象标签。方案中的 AI 只负责理解故事、辅助匹配已有歌曲，不承担生成歌曲的任务；当前 Demo 使用本地关键词与标签规则模拟匹配。

![匹配结果及原因说明](https://github.com/user-attachments/assets/9ea0c6b5-3791-4427-9762-bc7e3ceadf66)

*图 3：匹配理由说明答案与故事怎样影响结果。歌曲、歌词、音乐人与“已有多少人”均为虚构演示，试听由浏览器合成示意音乐。*

### 3. 分享自愿，将奖励连接到收听

分享卡保留歌名与歌词，不显示故事原文，让用户可以分享共鸣，同时保留私人表达。

抽奖机会则与收听进度关联：方案设定每天听满 15 分钟获得一次机会，活动期最多七次。这个机制希望鼓励回访与收听，其实际效果仍需正式活动数据验证。

## 四、用 XMind 把活动规则落实到页面

活动方案需要进一步回答：用户从哪里进入、每一步看到什么、点击后去哪里、遇到异常怎么办。

我使用 XMind 将交互模型拆成三个分支：

- **全局文案：** 统一主题、按钮、加载提示、结果说明和异常提示。
- **页面跳转逻辑：** 梳理答题、领歌、听歌、写故事、分享、领奖等路径，以及返回和再次参与的分支。
- **页面交互和功能：** 明确进度反馈、输入限制、隐私授权、超时处理与抽奖条件。

![XMind 交互模型节点整理图](https://github.com/user-attachments/assets/a4cb11ea-d54a-4eda-985b-491410f1276d)

*图 6：根据本人 XMind 原文件节点重新排版的节选，展示策划阶段的交互拆解，并非 XMind 软件截图。原文件另包含营销活动策划框架，梳理目标人群、渠道、指标、预算与风险。*

从导图到 Demo，我继续调整了具体路径。例如，早期导图允许先领歌再写故事，当前 Demo 将可跳过的故事页放在首次匹配之前；导图曾考虑分享时可选显示故事，当前 Demo 统一不显示原文。

导图中的登录领奖、App 唤起、真实版权曲库、AI 超时降级等属于方案设想，并非当前原型已经接入的能力。

## 五、把方案做成可体验、可收集反馈的原型

我将核心路径实现为 HTML 交互 Demo：

**活动首页 → 五道场景题 → 选填故事 → 匹配结果 → 试听、分享或抽奖 → 反馈与测试记录。**

页面采用移动活动页布局，电脑浏览器中以居中手机框展示，手机端可直接体验。当前原型无需账号，不依赖在线模型或数据库，便于邀请他人尝试。

除了主流程，我也设计了反馈问卷、可复制测试记录与本机测试汇总，用于观察：

| 观察内容 | 想验证的问题 |
|---|---|
| 开始到领歌用时、完成率 | 流程是否容易完成，约一分钟的目标能否实现 |
| 故事填写率、字数、换歌次数 | 用户是否愿意表达，结果是否符合期待 |
| 试听、领券、分享入口点击 | 哪些环节能引起后续操作兴趣 |
| 整体评分、匹配贴合度、分享及参与意愿 | 用户如何评价玩法，哪些环节值得改进 |

原型中的本机汇总统计的是当前浏览器的测试会话，不是跨设备去重用户数。数据保存在本机浏览器，远程测试者可以复制记录后自行反馈；没有集中上传数据库。分享入口点击不等于真实分享，主观参与意愿也不等于实际留存。

## 六、产出与下一步

项目最终输出产品分析、用户调研、营销策略分析、活动策划四份报告，以及 XMind 交互模型与可交互网页原型，方案通过终期答辩。

试玩中收到的一个具体建议是增加点触反馈。下一步我会先完善按钮按压态、选项确认与关键结果反馈，再继续验证流程用时、故事填写意愿和匹配贴合度。

如果推进真实活动，则需要进一步核验曲库版权与权益发放规则，验证故事理解与匹配方案，并通过真实收听及后续留存衡量效果。活动预算、参与规模和增长指标目前均属方案测算或目标，不能作为已发生的成绩。

> **当前演示边界：** 本地规则匹配；曲目与歌词虚构；音频为合成示意；领券、分享、抽奖为模拟；数据仅在本机保存。故事理解模型、真实曲库、真实权益和平台回流属于后续接入设想。
