# 企智通｜企业 AI 平台的普通用户端设计

**让成熟的业务经验，成为更多员工可以复用的工作方法。**

## 一、为什么做企智通

企业引入 AI 后，员工并不一定就能顺利用起来。

不同员工的业务经验与 AI 使用能力存在差异。面对一个空白聊天框，用户仍然需要想清楚：该提供什么信息、如何描述任务、按照什么标准判断结果。对于不熟悉业务或提示词的员工，这些准备本身就有门槛。

与此同时，优秀员工已经积累了许多有效的工作方法，但这些经验往往分散在个人习惯、文档和一次次沟通中，难以被其他人直接复用。

因此，我在设计中关注的问题是：** 如何把经过实践的业务方法整理成可调用的工具，让更多员工能够低门槛地完成专业任务。**

企智通以具体业务任务为入口，通过 Agent 承载相应的提示词、判断维度与输出要求，减少员工每次从头组织任务的成本。

## 二、用两类 Agent，兼顾企业标准与个人习惯

企业需要统一的业务标准，员工也需要适合自己工作的工具。项目方案将 Agent 分为企业预设与员工自建两类。

| 类型 | 企业预设 Agent | 员工自建 Agent |
|---|---|---|
| 主要用途 | 沉淀组织认可的工作方法 | 保存个人高频任务与提示词 |
| 使用范围 | 全公司员工可见、可调用 | 仅本人可见、可调用 |
| 维护方式 | 管理员配置、修改与删除 | 创建者自行修改与删除 |

企业预设 Agent 可以将成熟的分析框架、工作步骤与输出格式封装起来，让缺少经验的员工也有清晰的起点。

个人 Agent 则允许员工保存自己反复调试过的提示词。例如，一个人经常需要按固定结构整理周报，就可以将任务要求保存下来，下一次补充具体材料即可使用。

**企业预设 Agent 提供共同标准，个人 Agent 让有效的个人方法得以持续复用。**

## 三、让用户先开始工作，再逐步获得更多控制

普通员工第一次打开产品时，通常更关心“我要完成什么”，而不是“应该选哪个模型”。

因此，普通用户端提供了一条尽量直接的使用路径：

**开启对话 → 使用默认模型或选择 Agent → 补充任务材料 → 查看并继续调整结果。**

选择 Agent 后，提示词自动带入输入框，用户可以在现有要求上补充信息，减少面对空白输入框时的犹豫。

![选择 Agent 后自动带入任务提示词](https://github.com/user-attachments/assets/e7cc30ef-8d62-43f5-b9a1-4c95a3766b4b)

*图 3：选择“店铺经营日报 Agent”后，任务要求自动带入输入框。用户补充具体材料即可开始，无须每次重新组织完整提示词。*

对于熟练用户，则保留模型切换、Agent 创建与编辑、快捷唤起等操作。常用任务可以通过 Agent 复用，高频操作可以通过快捷键完成。

历史对话支持搜索、重命名与删除，帮助用户重新找到过去的工作内容，让一次对话产生的价值能够延续到下一次使用。

这些交互共同服务于一个目标：** 让新手容易开始，也让熟练用户有继续提高效率的空间。**

## 四、两个关键产品取舍

### 1. MVP 阶段，是否开放员工自建 Agent

讨论中，研发提出过一个实际问题：开放创建能力后，用户可能建立大量重复、低质量或长期不用的 Agent，带来资源与管理负担。

我们最终保留了这项能力。

原因是，MVP 阶段需要先验证员工是否愿意将自己的 AI 工作方法保存下来，并在后续工作中反复使用。如果过早关闭创建入口，就难以观察这种需求。

初期通过“个人 Agent 仅本人可见”和提示词敏感词检查控制范围。数量配额、重复检测、长期未使用归档等机制，则留待真实使用情况出现后再判断是否需要。

这次取舍让我认识到：** MVP 要控制交付范围，也要保留验证核心价值所必需的能力。**

### 2. 用户删除对话后，记录是否应该彻底消失

从个人使用体验出发，删除历史对话意味着用户不希望它继续出现在自己的列表中。但企业还需要对异常行为、敏感内容与安全事件进行追溯。

最终方案将两件事分开处理：

- 用户侧删除后，对话从个人历史列表中移除。
- 企业后台保留相应记录，用于安全审计。

这个设计区分了用户界面的整理操作与企业数据的保留机制。同时，继续完善产品时，也需要明确告知用户记录的保留范围、期限和访问权限，使界面中的“删除”与实际行为保持一致。

## 五、企业 AI 还需要考虑哪些边界

在普通用户端之外，我也参与了企业权限与安全相关设计，包括角色隔离、敏感词检测、违规拒答、日志留痕、Token 使用监控与异常告警。

这些机制会影响普通员工的实际体验。例如，账号由企业统一配置，员工不能自行开放注册；模型使用会产生真实成本，需要让用户了解资源使用情况；敏感请求需要拒答并留下相应记录。

*图 4：账号设置集中提供密码修改、邮箱绑定与个人 Agent 管理入口。图中的验证码和通知设置仅作前端交互展示，不会实际发送邮件。*

在 Agent 能力设计中，我参与了上下文管理、记忆、自主循环与安全审批等讨论。我的关注点是：减少用户重复提供背景的成本，同时明确哪些操作必须由人确认。

对于未来连接企业系统后的外部发送、数据删除、金额操作等高风险动作，应当保留人工审批，避免将任务执行能力直接等同于不受限制的操作权限。

**这些是项目层面的产品设计与能力边界，个人前端 Demo 不承担真实的权限校验与安全执行。**

## 六、我如何推动方案落地

项目没有独立的 UI 团队，因此我需要将需求设计、页面交互与验收标准衔接起来。

- **需求拆解：** 根据客户诉求编写符合 INVEST 原则的用户故事，明确使用场景、业务规则与验收边界。
- **需求澄清与规划：** 每个迭代组织 4 次以上需求澄清会，参与故事点评估，结合团队容量与业务优先级确定交付范围，并协同 Scrum Master 推进任务分配与进度。
- **原型设计：** 使用 Figma 独立输出高保真 UI 原型，明确核心页面结构、操作路径和状态反馈。
- **测试验收：** 依据用户故事与验收标准开展 UAT，累计识别并推动闭环 20 多项会话交互、状态反馈、数据持久化及规则校验类缺陷，跟进修复与回归验证。

我完成了三个完整迭代周期的产品设计与协同工作，企智通正式产品完成部署上线并投入使用。我也输出了中期路演材料，通过站会、路演与干系人反馈持续整理后续迭代输入。

## 八、后续思考

如果继续迭代，我会优先验证 Agent 是否真正被持续使用：员工创建后会不会再次调用，企业预设 Agent 是否能覆盖高频任务，用户在哪些环节仍需要反复补充要求。

在此基础上，再考虑个人 Agent 的数量配额、归档与重复检测，以及如何将经过验证的个人方法整理为组织可以复用的能力。

对于企业安全，则进一步完善数据保留说明、管理员访问边界与高风险操作确认。产品既要帮助员工更容易完成工作，也要让用户清楚理解数据与操作的边界。
